Verification: One Counter, Default Translation Strategy

Re-verifies “End-to-End Comparison: One Counter, Default Translation Strategy” against a real running system, all four columns, using the custom otelcol-custom collector built from the krajorama/opentelemetry-collector-contrib branch krajo/job-instance-persistence (see otelcollector/). That branch implements Options A/B/C as three mutually-exclusive alpha feature gates, off by default:

  • Receiver: receiver.prometheusreceiver.jobInstanceOption{A,B,C}
  • Exporter: exporter.prometheusremotewrite.jobInstanceOption{A,B,C}

Setup: oteljob app — resource service.name="my_service", service.instance.id="my_id"; meter foo; Float64Counter("received_samples") with attribute a.a="b"; default SDK translation strategy (no --no-translation). Scraped by the collector as job_name="my_job", target oteljob:9464. Egress via the collector’s prometheus_remote_write exporter (native PRW translator — the code path this branch modifies) to the custom-built Prometheus (prometheus/, branch krajo/debug-otlp-rw-endpoint). All four variants were actually run in the compose stack (OTELCOL_FEATURE_GATES=<gate names> docker compose up -d otel-collector); nothing here is inferred from source alone.

This is the one place actual behavior diverges from what the source document’s table would suggest, and the reason AGENTS.md requires running each column rather than reasoning from the diff alone. Option C’s exporter-side logic (setJobAndInstanceLabels, Option C branch) decides “is identity declared?” by checking for the literal dotted resource keys service.name / service.instance.id. But under the default SDK translation strategy, those keys never reach the collector under that spelling at all — the SDK escapes them to service_name/service_instance_id before the scrape happens (see Step 2), and Option C’s receiver additionally never populates the dotted keys from job/instance (see [^1]). So haveServiceName/haveInstanceID are both false, the “declared identity” branch never fires, and the exporter falls through to the prometheus.job/prometheus.instance fallback pair — which numerically equals the scrape’s job/instance here, making the final series indistinguishable from Today, A, and B. The doc’s own note (d), about Option C’s mapping being “keyed on the negotiated escaping, not on the producer’s translation strategy,” describes a version of this exact gap for a fuller proposed implementation with escaping-aware Covered Label Mapping; this POC is simpler still — it has no escaping-awareness on either side, so the mismatch is unconditional under the default strategy, not merely escaping-dependent. Declared-first behavior would only be observable in this POC if the app’s Resource happened to expose literal dotted service.name/service.instance.id keys to the receiver, which does not happen under the default translation strategy (see the separate NoTranslation scenario instead).↩︎
