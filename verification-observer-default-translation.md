# Verification: Observer Use Case, Default Translation Strategy

Verifies [UseCases.md](UseCases.md)'s use case 3 — one process ([observer/main.go](observer/main.go)) reporting metrics about two other applications it observes, each with its own `job`/`instance` identity — under the SDK's **default** translation strategy, across all four collector options: Today (no gates), and the `krajo/job-instance-persistence` fork's Options A/B/C. Companion to [verification-observer-notranslation.md](verification-observer-notranslation.md) and the two single-app reports.

**Implementation**: two `sdkmetric.MeterProvider`s share one `prometheus.Registry`. Each has its own Resource — `service.name`/`service.instance.id` (the app's real identity) plus custom `job`/`instance` attributes (the identity the observer assigns it) — and its own exporter constructed with `WithRegisterer(sharedRegistry)` and `WithResourceAsConstantLabels(attribute.NewAllowKeysFilter("job", "instance"))`.

**Setup**: App 1 — `service.name="my_service1"`, `service.instance.id="my_id1"`, `job="my_job1"`, `instance="my_instance1"`, counter value `1`. App 2 — same shape with `_2`/`2`. Both: meter `foo`, `Float64Counter("received_samples")` with attribute `a.a="b"`. Scraped by the collector as `job_name="observer_job"`, target `observer:9464`, **`honor_labels: true`**. Egress via `prometheus_remote_write`. Each of the four columns was actually run (`OTELCOL_FEATURE_GATES=<gates> docker compose --profile observer up -d --force-recreate observer otel-collector prometheus`), with Prometheus's storage wiped between captures.

**Methodology note**: `otelcol-config.compose.yaml` keeps *both* scrape jobs (`my_job` → `oteljob:9464`, `observer_job` → `observer:9464`) configured regardless of active profile. Under the `observer` profile `oteljob` doesn't exist, so `my_job` fails every cycle — but the failed target still gets a real (not stale) `up=0` data point, Resource, and synthesized `target_info`, for the same reason documented in [verification-observer.md](verification-observer-notranslation.md)'s predecessor: `addResourceTargetInfo` unconditionally synthesizes `target_info` from any Resource with a data point. It's excluded from the tables below since it isn't part of this use case. Because `CreateResource` runs once per unique `(job, instance)` pair found in the scrape (not once per scrape target — `honor_labels` preserves each app's own labels), the collector's per-app Options A/B/C behavior applies independently to App 1's Resource, App 2's Resource, *and* the scrape-metadata Resource (`observer_job`/`observer:9464`, which carries only `up`/`scrape_*` metrics that have no per-app `job`/`instance` override).

## Footnotes

[^1]: This is the observer-specific, and rather clean, illustration of the design document's point that "with never-derive in effect, an undeclared target yields a Resource with no `service.*` at all" (see the `Preserving Prometheus Job and Instance in OTLP Translation.md` doc, around line 485). The single-app reports never showed a fully service-less Resource because their one scrape target always had *some* signal it could pick up (either the app's own `target_info`, or nothing to speak of); here, the scrape-metadata Resource has no `target_info` sample of its own — the two apps' `target_info` samples get attributed to *their own* per-series Resources instead (see the methodology note) — so it's the one Resource in this whole set of reports with no identity attributes at all beyond the reserved pair.

[^2]: Same reasoning as `verification-default-translation.md`'s footnote 2: Option A/B's pair-first lookup (`setJobAndInstanceFromPair`) uses the bare/namespaced pair verbatim when present, and here the receiver populated the pair and the legacy `service.name`/`service.instance.id` fields with the *same* values (`my_job1`/`my_instance1`), so the two are indistinguishable in the final series.

[^3]: Unlike the single-app default-translation report — where Option C's exporter-side "is identity declared?" check never fires (because the SDK's default strategy escapes the app's declaration to `service_name`/`service_instance_id`, a key the check doesn't look for) and it silently falls back to the *scrape's* own `job`/`instance` — here that same fallback lands on the *correct* value. That's not because Option C's declared-identity detection started working: App 1's Resource has no dotted `service.name`/`service.instance.id` at all (see Step 3), so `haveServiceName`/`haveInstanceID` are still both false and the "declared identity" branch still never fires. It's because the reserved-pair fallback it uses instead (`prometheus.job`/`prometheus.instance`) was populated by `CreateResource` with `my_job1`/`my_instance1` — the value this specific use case wants — rather than a job-config-derived string. Change what value flows into the reserved pair (as the standalone/observer split does) and Option C's fallback path produces whatever that is, correct or not; it isn't reading the app's declaration either way.
