# Verification: Observer Use Case, Default Translation Strategy

Verifies [UseCases.md](UseCases.md)'s use case 3 — one process ([observer/main.go](observer/main.go)) reporting metrics about two other applications it observes, each with its own `job`/`instance` identity — under the SDK's **default** translation strategy, using the `krajo/job-instance-persistence` fork's Options B, C, and C1 (rebuilt against commit `78a1b6d`, "Add POC option C1"; see [verification-default-translation.md](verification-default-translation.md) for why Option A is omitted and what C1 is), alongside **Current** (today's collector behavior, no gates). Companion to [verification-observer-notranslation.md](verification-observer-notranslation.md) and the two single-app reports.

**Implementation**: two `sdkmetric.MeterProvider`s share one `prometheus.Registry`. Each has its own Resource — `service.name`/`service.instance.id` (the app's real identity) plus custom `job`/`instance` attributes (the identity the observer assigns it) — and its own exporter constructed with `WithRegisterer(sharedRegistry)` and `WithResourceAsConstantLabels(attribute.NewAllowKeysFilter("job", "instance"))`.

**Setup**: App 1 — `service.name="my_service1"`, `service.instance.id="my_id1"`, `job="my_job1"`, `instance="my_instance1"`, counter value `1`. App 2 — same shape with `_2`/`2`. Both: meter `foo`, `Float64Counter("received_samples")` with attribute `a.a="b"`. Scraped by the collector as `job_name="observer_job"`, target `observer:9464`, **`honor_labels: true`**. Egress via `prometheus_remote_write`. Each column was actually run (`OTELCOL_FEATURE_GATES=<gates> docker compose --profile observer up -d --force-recreate observer otel-collector prometheus`), with Prometheus's storage wiped between captures.

**Methodology note**: `otelcol-config.compose.yaml` keeps *both* scrape jobs configured regardless of active profile; the inactive `my_job`/`oteljob:9464` target's benign `up=0` + synthesized `target_info` is excluded from the tables below (see the single-app report's methodology note for why it's real, not stale, data). Because `CreateResource` runs once per unique `(job, instance)` pair found in the scrape (`honor_labels` preserves each app's own labels), the collector's per-app option behavior applies independently to App 1's Resource, App 2's Resource, *and* the scrape-metadata Resource (`observer_job`/`observer:9464`, covering only `up`/`scrape_*` metrics with no per-app `job`/`instance` override).

## Footnotes

[^1]: Same mechanism as [verification-default-translation.md](verification-default-translation.md)'s footnote 1, operating on App 1's own per-series Resource instead of the whole scrape target: `AddTargetInfo`'s covered-name recognition (added in commit `78a1b6d`) canonicalizes the flattened `service_name`/`service_instance_id` labels from App 1's `target_info` sample into the dotted `service.name`/`service.instance.id` keys, which `CreateResource`'s never-derive had left absent.

[^2]: This mirrors the previous version of this report's finding about Option C's scrape-metadata Resource: it has no `target_info` sample of its own (App 1 and App 2's samples are attributed to their own per-series Resources, not this one), so there's nothing for covered-name recognition to act on — it's genuinely service-less under both C and C1, identically.

[^3]: This is the reverse of the single-app report's finding, and the central result of this one: fixing Option C's receiver to recognize flattened covered names as declared identity is a *regression* for the observer use case specifically. The exporter-side check (`setJobAndInstanceLabels`, unchanged by this commit) has always read "declared identity" off the literal presence of dotted `service.name`/`service.instance.id` — it has no way to know that in this Resource, the "declaration" isn't the entity's own honest identity claim but an artifact of an observer app deliberately assigning a *different* identity than the one it's reporting about. Options B and C1 happen to sidestep this because they never populate those dotted keys via recognition in the first place; Option C actively creates the collision it's trying to solve elsewhere, one layer up.
