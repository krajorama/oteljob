# Verification: Observer Use Case, Default Translation Strategy

Verifies [UseCases.md](UseCases.md)'s use case 3 — one process ([observer/main.go](observer/main.go)) reporting metrics about two other applications it observes, each with its own `job`/`instance` identity — under the SDK's **default** translation strategy, using the `krajo/job-instance-persistence` fork's Options B, C, and C1 (rebuilt against commit `53af873`; see [verification-default-translation.md](verification-default-translation.md) for why Option A is omitted), alongside **Current** (today's collector behavior, no gates). Companion to [verification-observer-notranslation.md](verification-observer-notranslation.md) and the two single-app reports.

**This supersedes the previous version of this report**, which was verified against commit `78a1b6d`. Three commits have landed since — see [verification-default-translation.md](verification-default-translation.md) for the full list — the one that matters here is `ec7a8eb4f3`: Option B's receiver-side `CreateResource` no longer defaults job→`service.name`/`service.instance.id`, matching C/C1's "never-derive" behavior. This changes Option B's OTLP Resource shape (point 3) without changing the previously-published wire outcome (point 4), and it makes Option B and Option C1 converge completely — see the results and footnotes below.

**Implementation**: two `sdkmetric.MeterProvider`s share one `prometheus.Registry`. Each has its own Resource — `service.name`/`service.instance.id` (the app's real identity) plus custom `job`/`instance` attributes (the identity the observer assigns it) — and its own exporter constructed with `WithRegisterer(sharedRegistry)` and `WithResourceAsConstantLabels(attribute.NewAllowKeysFilter("job", "instance"))`.

**Setup**: App 1 — `service.name="my_service1"`, `service.instance.id="my_id1"`, `job="my_job1"`, `instance="my_instance1"`, counter value `1`. App 2 — same shape with `_2`/`2`. Both: meter `foo`, `Float64Counter("received_samples")` with attribute `a.a="b"`. Scraped by the collector as `job_name="observer_job"`, target `observer:9464`, **`honor_labels: true`**. Egress via `prometheus_remote_write` (default translation strategy, so none of the new `OTELCOL_RW_*` env vars are needed here — see the `NoTranslation` companion report for where they matter). Each column was actually run (`OTELCOL_FEATURE_GATES=<gates> docker compose --profile observer down && ... up -d`), with Prometheus's storage wiped between captures by fully recreating the stack.

**Methodology note**: `otelcol-config.compose.yaml` keeps *both* scrape jobs configured regardless of active profile; the inactive `my_job`/`oteljob:9464` target's benign `up=0` + synthesized `target_info` is excluded from the tables below, as is the `observer_job` scrape-metadata Resource's own `up`/`scrape_*` series (shown separately as its own row at point 3, since its shape also varies by option, but omitted from point 4 since it carries no per-app `job`/`instance` information).

## Footnotes

[^1]: Since commit `ec7a8eb4f3`, `CreateResource` no longer defaults job→`service.name`/`service.instance.id` for B, C, or C1 — all three now start from the same never-derive baseline. B and C1 both lack covered-name recognition, so with no recognition step to differ on, their receiver-side Resource for App 1/App 2 is now byte-identical (previously B additionally carried a job-derived `service.name`/`service.instance.id` pair that C1 didn't). The scrape-metadata Resource has no `target_info` sample of its own for any option to act on, so B, C, and C1 all reduce to the same shape there too — this was already true for B vs. C/C1 under the old code by coincidence (nothing to default *from* target_info either way), but is now true for the identical underlying reason across all three.

[^2]: The exporter-side logic (`setJobAndInstanceLabels`) is unchanged by any of the three recent commits: Option C's declared-identity branch checks whether `service.name`/`service.instance.id` are present and, if so, always derives `job`/`instance` from them — this is what "breaks" the observer use case, exactly as documented previously. What's new is that Option B's *series* output is now provably a receiver-side-only change: `CreateResource` no longer needs to default job-derived `service.name`/`service.instance.id` for the namespaced pair to win at the exporter (`setJobAndInstanceFromPair` looks up `prometheus.job`/`prometheus.instance` directly, unconditionally on anything else in the Resource), so removing that defaulting was safe — the wire output for B was never actually depending on it.
