# Verification: One Counter, `NoTranslation` Strategy

Re-verifies ["End-to-End Comparison: One Counter, `NoTranslation` Strategy"](../../open-telemetry/opentelemetry-go/Preserving%20Prometheus%20Job%20and%20Instance%20in%20OTLP%20Translation.md#end-to-end-comparison-one-counter-notranslation-strategy) against a real running system, all four columns, using the `oteljob` app's `-no-translation` flag (`main.go`) and the custom `otelcol-custom` collector built from the [`krajorama/opentelemetry-collector-contrib` branch `krajo/job-instance-persistence`](https://github.com/krajorama/opentelemetry-collector-contrib/tree/krajo/job-instance-persistence). The doc traces only the `allow-utf-8`-negotiated row of its escaping matrix (the one row where the app's declaration collides with the scrape identity); this report reproduces exactly that row, and confirms it is in fact the negotiated scheme in this system (see Setup).

**Setup**: `oteljob` started with `-no-translation=true` (`docker-compose.yaml`, `OTELJOB_NO_TRANSLATION=true`) — resource `service.name="my_service"`, `service.instance.id="my_id"`; meter `foo`; `Float64Counter("received_samples")` with attribute `a.a="b"`. Scraped by the collector as `job_name="my_job"`, target `oteljob:9464`. Confirmed via `oteljob`'s own request logging that the collector's real scrape request carries `Accept: application/openmetrics-text;version=1.0.0;escaping=allow-utf-8;q=0.6,application/openmetrics-text;version=0.0.1;q=0.5,text/plain;version=1.0.0;escaping=allow-utf-8;q=0.4,text/plain;version=0.0.4;q=0.3,*/*;q=0.2` — OpenMetrics 1.0 + `allow-utf-8` is the top preference, matching the doc's stated scrape default. Egress via the collector's `prometheus_remote_write` exporter to the custom-built Prometheus, as in the default-translation report. All four variants were actually run in the compose stack (`OTELJOB_NO_TRANSLATION=true OTELCOL_FEATURE_GATES=<gates> docker compose up -d`), with Prometheus's storage wiped (`--force-recreate prometheus`) between each variant to avoid stale series from a prior run contaminating the query results — an early capture without this step returned duplicate/stale series and had to be redone.

## Footnotes

[^1]: `oteljob`'s `/metrics` handler (`main.go`) is built on the bare `promhttp.Handler()`. In `github.com/prometheus/client_golang@v1.24.1` (`prometheus/promhttp/http.go`), that handler only negotiates OpenMetrics when constructed via `HandlerFor(..., HandlerOpts{EnableOpenMetrics: true})`; the zero-config `Handler()` always calls `expfmt.Negotiate` (never `NegotiateIncludingOpenMetrics`), so it *always* falls back to legacy `text/plain;version=0.0.4` — confirmed by curling with the collector's exact `Accept` header and checking the response's `Content-Type` verbatim. The `escaping=allow-utf-8` parameter is still honored (dotted keys appear on the wire), but the OpenMetrics-specific rule the source document's note (g) relies on — a counter family without a `_total` suffix gets typed `unknown` — is an OpenMetrics-exposition-format rule and never fires against `text/plain` 0.0.4. This is why `DataType` stays `Sum`/`counter` here instead of degrading to `Gauge`/`unknown` as the doc's table predicts, and it is option-independent (same root cause, same effect, in all four columns).

[^2]: The receiver's own logic for this collision is *entirely unmodified* by the `krajo/job-instance-persistence` branch: `AddTargetInfo` (`receiver/prometheusreceiver/internal/transaction.go`) copies every scraped `target_info` label except `job`/`instance`/`__name__` onto the Resource verbatim via `attrs.PutStr(lbl.Name, lbl.Value)`. Because `NoTranslation` + `allow-utf-8` means the label arrives spelled exactly `service.name`/`service.instance.id` (dotted), this collides with the same dotted keys `CreateResource` populates from the job/instance defaulting (Today, A, B) or simply fills in an otherwise-absent key (Option C). The three options only change what `CreateResource` puts there *first*; they do not change this collision mechanism at all.

[^3]: The doc's own table predicts metric name `foo` (no `_total` suffix) for this scenario, reasoning from the OpenMetrics `unknown`-type degradation described in its note (g). Because that degradation never happens here (see [^1]), the OTLP metric keeps its genuine `Sum`/counter type, and the collector's `prometheus_remote_write` exporter — `add_metric_suffixes: true` by default — adds the `_total` suffix it would add to any real counter. So the actual series name is `received_samples_total`, not `received_samples`, in all four columns; this is a second, causally-linked consequence of the same root cause as [^1], not a new discrepancy.

[^4]: `identifyingAttrNames` (`pkg/translator/prometheusremotewrite/helper.go`) always includes the baseline `service.namespace`/`service.name`/`service.instance.id` in the set of attributes excluded from `target_info`'s ordinary labels, for every option — Option A only *adds* `job`/`instance` to that exclusion set, it never removes the baseline three. The source document's note (i) calls for Option A/B implementations to "stop suppressing `service.name`/`service.instance.id`" so they appear as ordinary `target_info` labels; this POC does not implement that part of the proposal, so `service_name`/`service_instance_id` never appear on `target_info` under Option A or B, regardless of translation strategy.

[^5]: Same reasoning as the default-translation report: `setJobAndInstanceFromPair` (Option B branch) uses `prometheus.job`/`prometheus.instance` verbatim when present, and here they hold the same values (`my_job`/`oteljob:9464`) the bare pair holds under Option A, so the two are indistinguishable in the final series.

[^6]: This is the scenario where Option C's exporter-side "is identity declared?" check (`setJobAndInstanceLabels`, Option C branch) actually finds what it's looking for. It tests for the literal dotted resource keys `service.name`/`service.instance.id`. Under the *default* translation strategy those keys never reach the collector under that spelling (see [`verification-default-translation.md`](verification-default-translation.md), footnote 3); under `NoTranslation` + `allow-utf-8` they do, because nothing escapes them between the SDK and the receiver (see [^2]). So `haveServiceName`/`haveInstanceID` are both true here, the exporter takes the "declared identity" branch (unchanged legacy derivation: `job`/`instance` come from `service.name`/`service.instance.id`), and `identifyingAttrNames`'s Option C branch — which only excludes the reserved pair when the Resource is *undeclared* — leaves `prometheus.job`/`prometheus.instance` in target_info's ordinary attributes. Both halves of "declared-first" (series identity from the declaration, reserved pair demoted to metadata) match the source document's own prediction for this column almost exactly, modulo the metric-name-suffix and extra `telemetry_sdk_*` labels already explained above.
