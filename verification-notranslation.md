# Verification: One Counter, `NoTranslation` Strategy

Re-verifies ["End-to-End Comparison: One Counter, `NoTranslation` Strategy"](../../open-telemetry/opentelemetry-go/Preserving%20Prometheus%20Job%20and%20Instance%20in%20OTLP%20Translation.md#end-to-end-comparison-one-counter-notranslation-strategy) against a real running system, using the `oteljob` app's `-no-translation` flag (`main.go`) and the custom `otelcol-custom` collector built from [`krajorama/opentelemetry-collector-contrib` branch `krajo/job-instance-persistence`](https://github.com/krajorama/opentelemetry-collector-contrib/tree/krajo/job-instance-persistence), rebuilt against commit `53af873`.

**This supersedes the previous version of this report** in two ways:

1. **The harness itself was fixed.** The previous report's footnote 4 flagged that the collector's `prometheus_remote_write` exporter silently stayed on the default `UnderscoreEscapingWithSuffixes` translation strategy regardless of the app's `-no-translation` flag — nothing in `docker-compose.yaml`/`otelcol-config.compose.yaml` ever configured the exporter's own `translation_strategy`. That gap is now closed: the exporter's `translation_strategy` and `protobuf_message` are configurable via `OTELCOL_RW_TRANSLATION_STRATEGY`/`OTELCOL_RW_PROTOBUF_MESSAGE` (see [README.md](README.md)), and this run sets `NoTranslation` / `io.prometheus.write.v2.Request` on the exporter to actually match the app's setting. `NoTranslation` requires Prometheus Remote Write 2.0, which itself requires the alpha `exporter.prometheusremotewritexporter.enableSendingRW2` feature gate.
2. **Three upstream commits landed** on the branch since the previously-verified `78a1b6d` — see [verification-default-translation.md](verification-default-translation.md) for the receiver-side one (`ec7a8eb4f3`); the two that matter most here are `674aa93d65` (exporter/translator: `target_info` attribute suppression is now precise, not blanket) and especially `e99353caad` (exporter/translator: `target_info`'s own label *names* now respect the configured `translation_strategy` instead of always being hard-flattened to underscores).

Between the harness fix and these two commits, this report's point-4 results are qualitatively different from the previous version's — not just refinements.

**Setup**: `oteljob` started with `-no-translation=true` (`OTELJOB_NO_TRANSLATION=true`) — resource `service.name="my_service"`, `service.instance.id="my_id"`; meter `foo`; `Float64Counter("received_samples")` with attribute `a.a="b"`. Scraped by the collector as `job_name="my_job"`, target `oteljob:9464`. Confirmed via `oteljob`'s own request logging that the collector's real scrape request carries `Accept: application/openmetrics-text;version=1.0.0;escaping=allow-utf-8;q=0.6,application/openmetrics-text;version=0.0.1;q=0.5,text/plain;version=1.0.0;escaping=allow-utf-8;q=0.4,text/plain;version=0.0.4;q=0.3,*/*;q=0.2` — OpenMetrics 1.0 + `allow-utf-8` is the top preference, matching the doc's stated scrape default; point 2 below was curled with that exact header. Egress via `prometheus_remote_write`, configured with `OTELCOL_RW_TRANSLATION_STRATEGY=NoTranslation`, `OTELCOL_RW_PROTOBUF_MESSAGE=io.prometheus.write.v2.Request`, and (for all four columns, since RW2 is needed regardless of job/instance option) `OTELCOL_FEATURE_GATES` including `exporter.prometheusremotewritexporter.enableSendingRW2`. All four columns were actually run, with Prometheus's storage wiped between captures by fully recreating the stack (no persistent volume).

## Footnotes

[^1]: `oteljob`'s `/metrics` handler (`main.go`) is built on the bare `promhttp.Handler()`, which never negotiates OpenMetrics (see `verification-default-translation.md`'s sibling report for the same finding under the default strategy). The `escaping=allow-utf-8` parameter is still honored (dotted keys appear on the wire), but the OpenMetrics-only "counter without `_total` degrades to `unknown`" rule never fires against the `text/plain` 0.0.4 fallback — hence `DataType` stays `Sum`/`counter`, option-independently. With the harness fix, this now also holds at point 4: the real series name is `received_samples` (no `_total`), matching the doc's own prediction — the previous report's footnote 4, which explained away a spurious `_total` the exporter was adding, no longer applies.

[^2]: The receiver's collision mechanism is unchanged: `AddTargetInfo` copies the app's `target_info` sample onto the Resource, and since `NoTranslation` means it arrives spelled exactly `service.name`/`service.instance.id` (dotted), it overwrites whatever `CreateResource` put under those same keys — nothing, for the no-gate default path (which sets `service.name`/`service.instance.id` from job/instance, then gets overwritten by the app's own declaration).

[^3]: As of `ec7a8eb4f3`, `CreateResource` no longer defaults job→`service.name`/`service.instance.id` for B, C, or C1 — all three start from the same never-derive baseline, setting only the namespaced pair. Since `NoTranslation` means the app's `target_info` sample already arrives with the exact dotted spelling `AddTargetInfo` writes, there is nothing for covered-name recognition to do differently — B, C, and C1's receiver-side Resource is now identical in this scenario. (Contrast with `verification-default-translation.md`, where the default translation strategy flattens the app's declaration first, so C's recognition step visibly matters.)

[^4]: This is the fix from `674aa93d65` and `e99353caad` working together, and it is directly visible on the wire for the first time in this series of reports: previously, Option A/B's `target_info` suppression logic unconditionally treated `service.namespace`/`service.name`/`service.instance.id` as "identity" attributes to strip, and separately the label-name translation for `target_info` was hardcoded to underscore-sanitize regardless of `translation_strategy`. Now suppression is precise (only the attribute actually consumed as job/instance identity is stripped) and label names respect `NoTranslation`, so declared identity survives on `target_info` as ordinary, correctly-dotted attributes in both the B and C columns.

[^5]: Under `NoTranslation` there is no flattened spelling for covered-name recognition to canonicalize — the app's declaration already arrives dotted — so C and C1 converge, exactly as before. What's new is that this shared C/C1 behavior no longer also matches B (see [^3]): before `ec7a8eb4f3`, B's extra job-derived defaulting made its Resource shape diverge from C1's, but its exporter-side output still happened to converge with C1's declared-identity outcome; now that B and C1 start from the same receiver-side baseline, their exporter-side *gate semantics* (pair-first vs. declared-first) are what actually distinguish them, and they correctly disagree on which identity wins the series.
