# Verification: One Counter, `NoTranslation` Strategy

Re-verifies ["End-to-End Comparison: One Counter, `NoTranslation` Strategy"](../../open-telemetry/opentelemetry-go/Preserving%20Prometheus%20Job%20and%20Instance%20in%20OTLP%20Translation.md#end-to-end-comparison-one-counter-notranslation-strategy) against a real running system, using the `oteljob` app's `-no-translation` flag (`main.go`) and the custom `otelcol-custom` collector built from the [`krajorama/opentelemetry-collector-contrib` branch `krajo/job-instance-persistence`](https://github.com/krajorama/opentelemetry-collector-contrib/tree/krajo/job-instance-persistence), rebuilt against commit `78a1b6d` ("Add POC option C1"). The doc traces only the `allow-utf-8`-negotiated row of its escaping matrix (the one row where the app's declaration collides with the scrape identity); this report reproduces exactly that row, and confirms it is in fact the negotiated scheme in this system (see Setup).

Only **B, C, and C1** are shown — see [verification-default-translation.md](verification-default-translation.md) for why "Today" and Option A are omitted, and for what Option C1 is (Option C's receiver-side behavior *before* commit `78a1b6d` added covered-name recognition — this report already covered it, just under the name "Option C").

**Setup**: `oteljob` started with `-no-translation=true` (`docker-compose.yaml`, `OTELJOB_NO_TRANSLATION=true`) — resource `service.name="my_service"`, `service.instance.id="my_id"`; meter `foo`; `Float64Counter("received_samples")` with attribute `a.a="b"`. Scraped by the collector as `job_name="my_job"`, target `oteljob:9464`. Confirmed via `oteljob`'s own request logging that the collector's real scrape request carries `Accept: application/openmetrics-text;version=1.0.0;escaping=allow-utf-8;q=0.6,...` — OpenMetrics 1.0 + `allow-utf-8` is the top preference, matching the doc's stated scrape default. Egress via `prometheus_remote_write`. All three columns were actually run, with Prometheus's storage wiped between captures.

## Footnotes

[^1]: `oteljob`'s `/metrics` handler (`main.go`) is built on the bare `promhttp.Handler()`, which never negotiates OpenMetrics (see `verification-default-translation.md`'s sibling report for the same finding under the default strategy). The `escaping=allow-utf-8` parameter is still honored (dotted keys appear on the wire), but the OpenMetrics-only "counter without `_total` degrades to `unknown`" rule never fires against the `text/plain` 0.0.4 fallback — hence `DataType` stays `Sum`/`counter`, option-independently.

[^2]: The receiver's collision mechanism is unchanged by commit `78a1b6d`'s addition for the *undeclared* path, but Option B doesn't take that path at all: `CreateResource` still defaults `service.name`/`service.instance.id` from job/instance for B, and `AddTargetInfo` still overwrites them with the app's declaration for every option that leaves them derived in the first place. Nothing about covered-name recognition changes this, because recognition only matters when `CreateResource` left the dotted keys *absent* (Option C/C1's never-derive) — Option B never does that.

[^3]: This is the central finding of this report: **Option C's new covered-name recognition is a no-op under `NoTranslation`.** Recognition exists to canonicalize a *flattened* `service_name`/`service_instance_id` label into the dotted `service.name`/`service.instance.id` keys the exporter checks for. Under `NoTranslation`, the SDK never flattens anything — `target_info` already carries the dotted spelling directly (see Step 2) — so there is no flattened alias for recognition to canonicalize, and `addTargetInfoWithCoveredNameRecognition`'s single-spelling case reduces to exactly the same `attrs.PutStr` the old verbatim-copy loop would have done. C and C1 are therefore byte-identical here, and — because the declared-identity check already found what it needed even before this commit (see [verification-default-translation.md](verification-default-translation.md)'s original analysis, where `NoTranslation` was the one strategy where the pre-C1 "Option C" already achieved declared-first) — both are also identical to what Option B already produces once the collision is accounted for. The interesting divergence between C and C1 is specific to the *default* translation strategy; see the companion report.

[^4]: The doc's own table predicts metric name `foo` (no `_total` suffix), reasoning from an OpenMetrics-only type degradation that doesn't apply here — see [^1]. The collector's `add_metric_suffixes: true` default re-adds `_total` to what remains a genuine counter, so the real series name is `received_samples_total` throughout.
