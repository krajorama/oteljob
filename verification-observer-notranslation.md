# Verification: Observer Use Case, `NoTranslation` Strategy

Verifies [UseCases.md](UseCases.md)'s use case 3 — one process ([observer/main.go](observer/main.go)) reporting metrics about two other applications it observes, each with its own `job`/`instance` identity — under the SDK's **`NoTranslation`** strategy, across all four collector options: Today (no gates), and the `krajo/job-instance-persistence` fork's Options A/B/C. Companion to [verification-observer-default-translation.md](verification-observer-default-translation.md).

**Implementation and setup**: identical to the default-translation report, with `OBSERVER_NO_TRANSLATION=true`. App 1 — `service.name="my_service1"`, `service.instance.id="my_id1"`, `job="my_job1"`, `instance="my_instance1"`, counter value `1` (App 2: same shape with `_2`/`2`). Scraped as `job_name="observer_job"`, target `observer:9464`, `honor_labels: true`, egress via `prometheus_remote_write`. All four columns were actually run, Prometheus's storage wiped between captures. Same methodology note as the default-translation report applies: the inactive `my_job`/`oteljob:9464` scrape target's benign `up=0` + synthesized `target_info` is excluded from the tables below.

## Footnotes

[^1]: Same collision mechanism as `verification-notranslation.md`'s footnote 2, recurring here per observed app: `CreateResource` first derives `service.name="my_job1"`/`service.instance.id="my_instance1"` from App 1's per-series labels (Today), or additionally stores the bare/namespaced pair alongside them (A/B) — the pair itself is untouched by what happens next. Then `AddTargetInfo` (`receiver/prometheusreceiver/internal/transaction.go`, unmodified) copies App 1's own `target_info` sample onto the *same* Resource verbatim except `job`/`instance`/`__name__`. Under `NoTranslation` that sample's covered attributes arrive spelled exactly `service.name`/`service.instance.id` (dotted — see Step 2), which collides with and overwrites whatever `CreateResource` just put there. The bare/namespaced pair, stored under different keys entirely, is never touched by this collision.

[^2]: Option C's `CreateResource` never populates `service.name`/`service.instance.id` in the first place (never-derive), so there's nothing for `AddTargetInfo` to collide with — it just fills in the app's declared identity cleanly onto an otherwise-empty pair of keys. This is the one column, in either report, where the receiver-side Resource contains full, uncorrupted app identity *and* the observer's own pair side by side.

[^3]: See `verification-notranslation.md`'s footnote 1 for the root cause (bare `promhttp.Handler()`/`HandlerFor` never enables OpenMetrics) and footnote 3 for why this means the collector's `prometheus_remote_write` exporter re-adds a `_total` suffix that the design document's own table doesn't predict for this scenario.

[^4]: This is a genuine, observer-specific finding beyond what either single-app report showed. `identifyingAttrNames` (`pkg/translator/prometheusremotewrite/helper.go`) always excludes the baseline `service.namespace`/`service.name`/`service.instance.id` from `target_info`'s ordinary attributes, and Option A/B additionally exclude the bare/namespaced pair (since it's consumed as identity). Here `service.name`/`service.instance.id` hold App 1's *real* declared values (`my_service1`/`my_id1`, per [^1]) — but because they're excluded unconditionally, not read and republished, that declaration is discarded rather than demoted to metadata. Contrast with the single-app `NoTranslation` report's Option A/B columns, where the pair and the (uncollided, job-derived) `service.name`/`service.instance.id` held *different* values and neither one was silently lost — there just was no separate "real identity" to lose in that scenario, since the single app's `service.name` normally *is* what the pair is competing with, not a bystander getting excluded along with it.

[^5]: Option C's exporter-side `setJobAndInstanceLabels` decides "is identity declared?" by checking whether `service.name`/`service.instance.id` are present at all — not by checking how they got there. Per [^2], Option C's receiver-side never-derive means these keys hold App 1's genuinely correct, uncollided values (`my_service1`/`my_id1`) here, same as they do under Today (where the check isn't gated by any option). Either way, `haveServiceName`/`haveInstanceID` read true, so the exporter takes the declared-identity branch and emits `job="my_service1"`/`instance="my_id1"` — the same outcome as Today, since both branches derive `job`/`instance` from `service.name`/`service.instance.id` identically. The difference from Today is only in `identifyingAttrNames`: Option C's branch excludes the reserved pair from ordinary `target_info` attributes *only* when the Resource is undeclared; since this Resource now counts as declared, the pair stays visible as `prometheus_job`/`prometheus_instance`, giving `target_info` a way to recover the observer's intended identity that Today's column doesn't have.
