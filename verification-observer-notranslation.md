# Verification: Observer Use Case, `NoTranslation` Strategy

Verifies [UseCases.md](UseCases.md)'s use case 4 — the observer use case under the SDK's **`NoTranslation`** strategy — using the `krajo/job-instance-persistence` fork's Options B, C, and C1 (rebuilt against commit `53af873`), alongside **Current** (no gates). Companion to [verification-observer-default-translation.md](verification-observer-default-translation.md).

**This supersedes the previous version of this report** in two ways, same as the single-app `NoTranslation` companion report:

1. **The harness was fixed**: the `prometheus_remote_write` exporter's `translation_strategy`/`protobuf_message` now actually track the observer's `-no-translation` flag (`OTELCOL_RW_TRANSLATION_STRATEGY=NoTranslation`, `OTELCOL_RW_PROTOBUF_MESSAGE=io.prometheus.write.v2.Request`, plus the `exporter.prometheusremotewritexporter.enableSendingRW2` feature gate) instead of silently staying on default translation — see [verification-notranslation.md](verification-notranslation.md) for the full explanation.
2. **Three upstream commits landed** since the previously-verified `78a1b6d` — see [verification-default-translation.md](verification-default-translation.md) for the full list. All three matter here, and together they produce this report's single most important new finding: **Option B now correctly serves the observer use case under `NoTranslation`, where it previously did not.**

**Implementation and setup**: identical to the default-translation companion report, with `OBSERVER_NO_TRANSLATION=true`. App 1 — `service.name="my_service1"`, `service.instance.id="my_id1"`, `job="my_job1"`, `instance="my_instance1"`, counter value `1` (App 2: same shape with `_2`/`2`). Scraped as `job_name="observer_job"`, target `observer:9464`, `honor_labels: true`, egress via `prometheus_remote_write`. All four columns were actually run, Prometheus's storage wiped between captures by fully recreating the stack. Same methodology note as the default-translation report applies re: the inactive `my_job`/`oteljob:9464` scrape target and the scrape-metadata Resource's `up`/`scrape_*` series.

## Footnotes

[^1]: Same mechanism as `verification-notranslation.md`'s footnote 3, applied per observed app: since `ec7a8eb4f3` removed Option B's job-derived defaulting, B/C/C1 all start from the same never-derive baseline, and since `NoTranslation` means the app's `target_info` sample already carries the exact dotted spelling `AddTargetInfo` writes, covered-name recognition (C's differentiator) has nothing to do — all three converge on the receiver side.

[^2]: See `verification-notranslation.md`'s footnote 1 for why `oteljob`-style OpenMetrics degradation doesn't apply here (bare `promhttp.HandlerFor`), and for why the harness fix means the real series name is `received_samples` (no spurious `_total`) throughout this report too.

[^3]: This is `674aa93d65` (precise `target_info` suppression) and `e99353caad` (UTF-8-respecting `target_info` label names) working together, directly visible on the wire: declared identity survives as ordinary, correctly-dotted `target_info` attributes rather than being stripped or corrupted to underscores.

[^4]: **This is the headline finding of this report.** In the previously-published version, Options B, C, and C1 all converged on the same (broken, for this use case) outcome under `NoTranslation` — Option B's extra job-derived `service.name`/`service.instance.id` collided with the app's own declaration the same way Current's did, so by the time `setJobAndInstanceLabels` ran, B's Resource looked no different from C's for the exporter's purposes. Now that `CreateResource` no longer performs that defaulting for B, there is no collision left to produce that accidental agreement: `setJobAndInstanceFromPair` (Option B) reads the always-present namespaced pair unconditionally and wins, while Option C/C1's declared-identity-first check (`setJobAndInstanceLabels`, unchanged by any of the three commits) still finds `service.name`/`service.instance.id` present and defers to them. The result is that B now does the *opposite* of C/C1 for this use case — correctly, since assigning a different identity than the observed entity's own is precisely what an observer needs, and that is exactly what Option B's "namespaced, pair-first" design was for.
