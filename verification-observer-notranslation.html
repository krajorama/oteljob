Verification: Observer Use Case, NoTranslation Strategy

Verifies UseCases.md’s use case 4 — the observer use case under the SDK’s NoTranslation strategy — using the krajo/job-instance-persistence fork’s Options B, C, and C1 (rebuilt against commit 53af873), alongside Current (no gates). Companion to verification-observer-default-translation.md.

This supersedes the previous version of this report in two ways, same as the single-app NoTranslation companion report:

  1. The harness was fixed: the prometheus_remote_write exporter’s translation_strategy/protobuf_message now actually track the observer’s -no-translation flag (OTELCOL_RW_TRANSLATION_STRATEGY=NoTranslation, OTELCOL_RW_PROTOBUF_MESSAGE=io.prometheus.write.v2.Request, plus the exporter.prometheusremotewritexporter.enableSendingRW2 feature gate) instead of silently staying on default translation — see verification-notranslation.md for the full explanation.
  2. Three upstream commits landed since the previously-verified 78a1b6d — see verification-default-translation.md for the full list. All three matter here, and together they produce this report’s single most important new finding: Option B now correctly serves the observer use case under NoTranslation, where it previously did not.

Implementation and setup: identical to the default-translation companion report, with OBSERVER_NO_TRANSLATION=true. App 1 — service.name="my_service1", service.instance.id="my_id1", job="my_job1", instance="my_instance1", counter value 1 (App 2: same shape with _2/2). Scraped as job_name="observer_job", target observer:9464, honor_labels: true, egress via prometheus_remote_write. All four columns were actually run, Prometheus’s storage wiped between captures by fully recreating the stack. Same methodology note as the default-translation report applies re: the inactive my_job/oteljob:9464 scrape target and the scrape-metadata Resource’s up/scrape_* series.

Now that CreateResource no longer performs that defaulting for B, there is no collision left to produce that accidental agreement: setJobAndInstanceFromPair (Option B) reads the always-present namespaced pair unconditionally and wins, while Option C/C1’s declared-identity-first check (setJobAndInstanceLabels, unchanged by any of the three commits) still finds service.name/service.instance.id present and defers to them. The result is that B now does the opposite of C/C1 for this use case — correctly, since assigning a different identity than the observed entity’s own is precisely what an observer needs, and that is exactly what Option B’s “namespaced, pair-first” design was for.↩︎
