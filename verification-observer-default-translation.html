Verification: Observer Use Case, Default Translation Strategy

Verifies UseCases.md’s use case 3 — one process (observer/main.go) reporting metrics about two other applications it observes, each with its own job/instance identity — under the SDK’s default translation strategy, using the krajo/job-instance-persistence fork’s Options B, C, and C1 (rebuilt against commit 53af873; see verification-default-translation.md for why Option A is omitted), alongside Current (today’s collector behavior, no gates). Companion to verification-observer-notranslation.md and the two single-app reports.

This supersedes the previous version of this report, which was verified against commit 78a1b6d. Three commits have landed since — see verification-default-translation.md for the full list — the one that matters here is ec7a8eb4f3: Option B’s receiver-side CreateResource no longer defaults job→service.name/service.instance.id, matching C/C1’s “never-derive” behavior. This changes Option B’s OTLP Resource shape (point 3) without changing the previously-published wire outcome (point 4), and it makes Option B and Option C1 converge completely — see the results and footnotes below.

Implementation: two sdkmetric.MeterProviders share one prometheus.Registry. Each has its own Resource — service.name/service.instance.id (the app’s real identity) plus custom job/instance attributes (the identity the observer assigns it) — and its own exporter constructed with WithRegisterer(sharedRegistry) and WithResourceAsConstantLabels(attribute.NewAllowKeysFilter("job", "instance")).

Setup: App 1 — service.name="my_service1", service.instance.id="my_id1", job="my_job1", instance="my_instance1", counter value 1. App 2 — same shape with _2/2. Both: meter foo, Float64Counter("received_samples") with attribute a.a="b". Scraped by the collector as job_name="observer_job", target observer:9464, honor_labels: true. Egress via prometheus_remote_write (default translation strategy, so none of the new OTELCOL_RW_* env vars are needed here — see the NoTranslation companion report for where they matter). Each column was actually run (OTELCOL_FEATURE_GATES=<gates> docker compose --profile observer down && ... up -d), with Prometheus’s storage wiped between captures by fully recreating the stack.

Methodology note: otelcol-config.compose.yaml keeps both scrape jobs configured regardless of active profile; the inactive my_job/oteljob:9464 target’s benign up=0 + synthesized target_info is excluded from the tables below, as is the observer_job scrape-metadata Resource’s own up/scrape_* series (shown separately as its own row at point 3, since its shape also varies by option, but omitted from point 4 since it carries no per-app job/instance information).
