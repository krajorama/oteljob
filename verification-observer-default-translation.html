Verification: Observer Use Case, Default Translation Strategy

Verifies UseCases.md’s use case 3 — one process (observer/main.go) reporting metrics about two other applications it observes, each with its own job/instance identity — under the SDK’s default translation strategy, using the krajo/job-instance-persistence fork’s Options B, C, and C1 (rebuilt against commit 78a1b6d, “Add POC option C1”; see verification-default-translation.md for why Option A is omitted and what C1 is), alongside Current (today’s collector behavior, no gates). Companion to verification-observer-notranslation.md and the two single-app reports.

Implementation: two sdkmetric.MeterProviders share one prometheus.Registry. Each has its own Resource — service.name/service.instance.id (the app’s real identity) plus custom job/instance attributes (the identity the observer assigns it) — and its own exporter constructed with WithRegisterer(sharedRegistry) and WithResourceAsConstantLabels(attribute.NewAllowKeysFilter("job", "instance")).

Setup: App 1 — service.name="my_service1", service.instance.id="my_id1", job="my_job1", instance="my_instance1", counter value 1. App 2 — same shape with _2/2. Both: meter foo, Float64Counter("received_samples") with attribute a.a="b". Scraped by the collector as job_name="observer_job", target observer:9464, honor_labels: true. Egress via prometheus_remote_write. Each column was actually run (OTELCOL_FEATURE_GATES=<gates> docker compose --profile observer up -d --force-recreate observer otel-collector prometheus), with Prometheus’s storage wiped between captures.

Methodology note: otelcol-config.compose.yaml keeps both scrape jobs configured regardless of active profile; the inactive my_job/oteljob:9464 target’s benign up=0 + synthesized target_info is excluded from the tables below (see the single-app report’s methodology note for why it’s real, not stale, data). Because CreateResource runs once per unique (job, instance) pair found in the scrape (honor_labels preserves each app’s own labels), the collector’s per-app option behavior applies independently to App 1’s Resource, App 2’s Resource, and the scrape-metadata Resource (observer_job/observer:9464, covering only up/scrape_* metrics with no per-app job/instance override).

Net effect App 1 and App 2 are cleanly distinguished by job/instance (my_job1/my_instance1 vs. my_job2/my_instance2), and each app’s real identity is queryable via target_info. Same wire output as Current; the OTLP Resource additionally carries an explicit namespaced pair, invisible on the wire. Breaks the use case. App 1 and App 2’s series now key on their own service.name/service.instance.id (my_service1/my_id1, my_service2/my_id2) — which, unlike the single-app report, is the wrong outcome here: the whole point of an observer is to assign its own identity to targets it doesn’t control, and this fix for the single-app collision actively defeats that. Reproduces the correct, intended output — the same output this report’s predecessor already documented under the name “Option C.”

Options B and C1 happen to sidestep this because they never populate those dotted keys via recognition in the first place; Option C actively creates the collision it’s trying to solve elsewhere, one layer up.↩︎
