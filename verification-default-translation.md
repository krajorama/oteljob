# Verification: One Counter, Default Translation Strategy

Re-verifies ["End-to-End Comparison: One Counter, Default Translation Strategy"](../../open-telemetry/opentelemetry-go/Preserving%20Prometheus%20Job%20and%20Instance%20in%20OTLP%20Translation.md#end-to-end-comparison-one-counter-default-translation-strategy) against a real running system, using the custom `otelcol-custom` collector built from the [`krajorama/opentelemetry-collector-contrib` branch `krajo/job-instance-persistence`](https://github.com/krajorama/opentelemetry-collector-contrib/tree/krajo/job-instance-persistence) (see [otelcollector/](otelcollector/)), rebuilt against commit `53af873` ("Update changelog with PR number #50435"). That branch implements Options A/B/C/C1 as four mutually-exclusive alpha feature gates, off by default:

- Receiver: `receiver.prometheusreceiver.jobInstanceOption{A,B,C,C1}`
- Exporter: `exporter.prometheusremotewrite.jobInstanceOption{A,B,C,C1}`

**This supersedes the previous version of this report**, which was verified against commit `78a1b6d`. Three commits have landed on the branch since then, all touching this report's results:

- `ec7a8eb4f3` (receiver): Option B's job→`service.name`/`service.instance.id` defaulting is now opt-in and **disabled by default** — Option B no longer defaults those attributes at all, matching Option C/C1's "never-derive" behavior on the receiver side.
- `674aa93d65` (exporter/translator): Option A/B's `target_info` attribute suppression now only suppresses the specific bare/namespaced attribute actually consumed as job/instance identity, instead of unconditionally suppressing `service.name`/`service.namespace`/`service.instance.id` regardless of whether they hold real declared identity.
- `e99353caad` (exporter/translator): `target_info`'s own label names now respect the configured `translation_strategy` (this one is invisible under the default strategy — its effect shows up in [verification-notranslation.md](verification-notranslation.md)).

Shown below: **Current** (today's collector behavior, no gates enabled) plus **B, C, and C1**. Option A is omitted — four option columns plus Current made the tables too wide, and its bare `job`/`instance` resource attributes aren't a shape that makes sense in the OTel data model to begin with.

**Setup**: `oteljob` app — resource `service.name="my_service"`, `service.instance.id="my_id"`; meter `foo`; `Float64Counter("received_samples")` with attribute `a.a="b"`; default SDK translation strategy (no `-no-translation`). Scraped by the collector as `job_name="my_job"`, target `oteljob:9464`. Egress via the collector's `prometheus_remote_write` exporter to the custom-built Prometheus (`prometheus/`, branch `krajo/debug-otlp-rw-endpoint`). All four columns were actually run in the compose stack (`OTELCOL_FEATURE_GATES=<gate names> docker compose --profile standalone down && ... up -d`), with Prometheus's storage wiped between captures by fully recreating the stack each time (Prometheus has no persistent volume, so a fresh container is an empty TSDB); nothing here is inferred from source alone.

## Footnotes

[^1]: `CreateResource` (`prom_to_otlp.go`) no longer defaults `service.name`/`service.instance.id` from `job`/`instance` for B, C, or C1 (only the no-gate default path still does). All three now start from the same never-derive baseline and only set the namespaced `prometheus.job`/`prometheus.instance` pair. They diverge solely in `AddTargetInfo` (`transaction.go`): B and C1 copy the app's `target_info` labels verbatim, landing under whatever spelling the SDK exposed them with — flattened `service_name`/`service_instance_id` under the default translation strategy. C instead runs `addTargetInfoWithCoveredNameRecognition`, recognizing that flattened spelling as an alias for the dotted `service.name`/`service.instance.id` and writing the canonical dotted key.

[^2]: **This is the headline finding of this report.** Before commit `ec7a8eb4f3`, Option B's `CreateResource` additionally set job-derived `service.name`/`service.instance.id` alongside the namespaced pair — a Resource shape distinct from C1's. Now that defaulting is gone, B and C1's receiver output is byte-identical, and since neither performs covered-name recognition, the exporter sees the same flattened (never-dotted) Resource in both cases: `setJobAndInstanceFromPair` (Option B's exporter logic, unconditional on declared identity) picks the namespaced pair, and C1's declared-identity check never fires because `service.name`/`service.instance.id` never arrive under that dotted spelling — the two options now agree at every step, not just on the wire.

[^3]: The exporter-side `target_info` attribute-suppression fix (`674aa93d65`) makes Option B's `target_info` handling correct-by-construction rather than correct-by-coincidence: it now suppresses only the specific namespaced pair actually consumed as identity, not every `service.*` key unconditionally, so declared identity reliably survives as ordinary `target_info` metadata regardless of what else is present on the Resource. In this single-app, default-translation scenario the visible output happens not to change, because the flattened `service_name`/`service_instance_id` keys were never the ones the old bug targeted in the first place — see [verification-notranslation.md](verification-notranslation.md) for a case where the fix's effect is directly visible on the wire.
