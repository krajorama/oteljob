# Verification: One Counter, Default Translation Strategy

Re-verifies ["End-to-End Comparison: One Counter, Default Translation Strategy"](../../open-telemetry/opentelemetry-go/Preserving%20Prometheus%20Job%20and%20Instance%20in%20OTLP%20Translation.md#end-to-end-comparison-one-counter-default-translation-strategy) against a real running system, using the custom `otelcol-custom` collector built from the [`krajorama/opentelemetry-collector-contrib` branch `krajo/job-instance-persistence`](https://github.com/krajorama/opentelemetry-collector-contrib/tree/krajo/job-instance-persistence) (see [otelcollector/](otelcollector/)), rebuilt against commit `78a1b6d` ("Add POC option C1"). That branch implements Options A/B/C/C1 as four mutually-exclusive alpha feature gates, off by default:

- Receiver: `receiver.prometheusreceiver.jobInstanceOption{A,B,C,C1}`
- Exporter: `exporter.prometheusremotewrite.jobInstanceOption{A,B,C,C1}`

Shown below: **Current** (today's collector behavior, no gates enabled) plus **B, C, and C1**. Option A is omitted — four option columns plus Current made the tables too wide, and its bare `job`/`instance` resource attributes aren't a shape that makes sense in the OTel data model to begin with. Option A's own results are unaffected by this update and remain available in git history.

**Option C1 is new**: as of commit `78a1b6d`, Option C's receiver-side (`AddTargetInfo`) gained "covered-name recognition" — it now recognizes `target_info`'s flattened `service_name`/`service_namespace`/`service_instance_id` labels as declaring the same identity as their dotted spelling, not just the literal dotted form. Option C1 is Option C *without* that recognition — i.e., exactly the old Option C behavior this report previously documented. The two share identical exporter-side (OTLP → Prometheus) logic; they differ only in what the receiver populates.

**Setup**: `oteljob` app — resource `service.name="my_service"`, `service.instance.id="my_id"`; meter `foo`; `Float64Counter("received_samples")` with attribute `a.a="b"`; default SDK translation strategy (no `-no-translation`). Scraped by the collector as `job_name="my_job"`, target `oteljob:9464`. Egress via the collector's `prometheus_remote_write` exporter to the custom-built Prometheus (`prometheus/`, branch `krajo/debug-otlp-rw-endpoint`). All four columns were actually run in the compose stack (`OTELCOL_FEATURE_GATES=<gate names> docker compose --profile standalone up -d --force-recreate oteljob otel-collector prometheus`), with Prometheus's storage wiped between captures; nothing here is inferred from source alone.

## Footnotes

[^1]: Both C and C1 share the same receiver-side "never-derive": `CreateResource` (`prom_to_otlp.go`) sets *only* `prometheus.job`/`prometheus.instance` from the scrape and leaves `service.name`/`service.instance.id` unset, regardless of which gate is on. The two options diverge only in `AddTargetInfo` (`transaction.go`): C1 copies every `target_info` label verbatim (the original, unmodified behavior), so the app's declaration lands under whatever spelling it was exposed with — here, flattened `service_name`/`service_instance_id`, since the SDK's default translation strategy escapes the dots before the scrape ever happens. C instead runs `addTargetInfoWithCoveredNameRecognition`, which recognizes `service_name`/`service_namespace`/`service_instance_id` as aliases of the dotted `service.name`/`service.namespace`/`service.instance.id` and writes the canonical dotted key (collapsing agreeing spellings, dropping disagreeing ones rather than guessing) — so the same input that leaves C1's Resource with flattened keys leaves C's Resource with dotted ones.

[^2]: `setJobAndInstanceFromPair`-style reasoning doesn't even apply to B here since B's own pair-first lookup (used elsewhere in this series of reports) isn't what's active for the *default*, no-gate path — rather, `CreateResource` under Option B stores the namespaced pair *alongside* the same job-derived `service.name`/`service.instance.id` that Current relies on, and the exporter's legacy derivation reads the latter regardless of gate. Since both hold the same value (`my_job`/`oteljob:9464`), B's extra pair is invisible on the wire and the two columns are byte-identical in the final series.

[^3]: The exporter-side logic is *unchanged* from what previously ran as "Option C": `setJobAndInstanceLabels`'s declared-identity branch simply checks whether `service.name`/`service.instance.id` (dotted) are present on the Resource, and derives `job`/`instance` from them if so. What changed is that the receiver now actually populates those dotted keys under the default translation strategy (see [^1]), so this check — which always existed — finally has something to find.

[^4]: This column is exactly what commit `78a1b6d`'s message describes: Option C's old behavior, preserved as its own gate. Compare directly against the original report content (still in git history) for Option C before this commit — the results are identical, because C1 *is* that old behavior, unchanged.
