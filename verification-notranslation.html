Verification: One Counter, NoTranslation Strategy

Re-verifies “End-to-End Comparison: One Counter, NoTranslation Strategy” against a real running system, using the oteljob app’s -no-translation flag (main.go) and the custom otelcol-custom collector built from krajorama/opentelemetry-collector-contrib branch krajo/job-instance-persistence, rebuilt against commit 53af873.

This supersedes the previous version of this report in two ways:

  1. The harness itself was fixed. The previous report’s footnote 4 flagged that the collector’s prometheus_remote_write exporter silently stayed on the default UnderscoreEscapingWithSuffixes translation strategy regardless of the app’s -no-translation flag — nothing in docker-compose.yaml/otelcol-config.compose.yaml ever configured the exporter’s own translation_strategy. That gap is now closed: the exporter’s translation_strategy and protobuf_message are configurable via OTELCOL_RW_TRANSLATION_STRATEGY/OTELCOL_RW_PROTOBUF_MESSAGE (see README.md), and this run sets NoTranslation / io.prometheus.write.v2.Request on the exporter to actually match the app’s setting. NoTranslation requires Prometheus Remote Write 2.0, which itself requires the alpha exporter.prometheusremotewritexporter.enableSendingRW2 feature gate.
  2. Three upstream commits landed on the branch since the previously-verified 78a1b6d — see verification-default-translation.md for the receiver-side one (ec7a8eb4f3); the two that matter most here are 674aa93d65 (exporter/translator: target_info attribute suppression is now precise, not blanket) and especially e99353caad (exporter/translator: target_info’s own label names now respect the configured translation_strategy instead of always being hard-flattened to underscores).

Between the harness fix and these two commits, this report’s point-4 results are qualitatively different from the previous version’s — not just refinements.

Setup: oteljob started with -no-translation=true (OTELJOB_NO_TRANSLATION=true) — resource service.name="my_service", service.instance.id="my_id"; meter foo; Float64Counter("received_samples") with attribute a.a="b". Scraped by the collector as job_name="my_job", target oteljob:9464. Confirmed via oteljob’s own request logging that the collector’s real scrape request carries Accept: application/openmetrics-text;version=1.0.0;escaping=allow-utf-8;q=0.6,application/openmetrics-text;version=0.0.1;q=0.5,text/plain;version=1.0.0;escaping=allow-utf-8;q=0.4,text/plain;version=0.0.4;q=0.3,*/*;q=0.2 — OpenMetrics 1.0 + allow-utf-8 is the top preference, matching the doc’s stated scrape default; point 2 below was curled with that exact header. Egress via prometheus_remote_write, configured with OTELCOL_RW_TRANSLATION_STRATEGY=NoTranslation, OTELCOL_RW_PROTOBUF_MESSAGE=io.prometheus.write.v2.Request, and (for all four columns, since RW2 is needed regardless of job/instance option) OTELCOL_FEATURE_GATES including exporter.prometheusremotewritexporter.enableSendingRW2. All four columns were actually run, with Prometheus’s storage wiped between captures by fully recreating the stack (no persistent volume).
