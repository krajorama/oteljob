Verification: One Counter, NoTranslation Strategy

Re-verifies “End-to-End Comparison: One Counter, NoTranslation Strategy” against a real running system, using the oteljob app’s -no-translation flag (main.go) and the custom otelcol-custom collector built from the krajorama/opentelemetry-collector-contrib branch krajo/job-instance-persistence, rebuilt against commit 78a1b6d (“Add POC option C1”). The doc traces only the allow-utf-8-negotiated row of its escaping matrix (the one row where the app’s declaration collides with the scrape identity); this report reproduces exactly that row, and confirms it is in fact the negotiated scheme in this system (see Setup).

Shown below: Current (no gates) plus B, C, and C1 — see verification-default-translation.md for why Option A is omitted, and for what Option C1 is (Option C’s receiver-side behavior before commit 78a1b6d added covered-name recognition — this report already covered it, just under the name “Option C”).

Setup: oteljob started with -no-translation=true (docker-compose.yaml, OTELJOB_NO_TRANSLATION=true) — resource service.name="my_service", service.instance.id="my_id"; meter foo; Float64Counter("received_samples") with attribute a.a="b". Scraped by the collector as job_name="my_job", target oteljob:9464. Confirmed via oteljob’s own request logging that the collector’s real scrape request carries Accept: application/openmetrics-text;version=1.0.0;escaping=allow-utf-8;q=0.6,... — OpenMetrics 1.0 + allow-utf-8 is the top preference, matching the doc’s stated scrape default. Egress via prometheus_remote_write. All four columns were actually run, with Prometheus’s storage wiped between captures.

Net effect Declared identity wins, and the scrape’s job/instance (my_job/oteljob:9464) are lost with no trace anywhere — no gate stored them for target_info to fall back on. Declared identity wins, same as Current, but the scrape’s job/instance at least survive as target_info metadata (prometheus_job/prometheus_instance), since Option B always stores the namespaced pair regardless of what’s declared. Identical outcome to Option B — under NoTranslation, covered-name recognition has nothing to do, since the declaration already arrives dotted. Identical outcome to Option B and Option C — the two-gate distinction this branch introduces is entirely invisible under NoTranslation.

  4. This is the central finding of this report: Option C’s new covered-name recognition is a no-op under NoTranslation. Recognition exists to canonicalize a flattened service_name/service_instance_id label into the dotted service.name/service.instance.id keys the exporter checks for. Under NoTranslation, the SDK never flattens anything — target_info already carries the dotted spelling directly (see Step 2) — so there is no flattened alias for recognition to canonicalize, and addTargetInfoWithCoveredNameRecognition’s single-spelling case reduces to exactly the same attrs.PutStr the old verbatim-copy loop would have done. C and C1 are therefore byte-identical here, and — because the declared-identity check already found what it needed even before this commit (see verification-default-translation.md’s original analysis, where NoTranslation was the one strategy where the pre-C1 “Option C” already achieved declared-first) — both are also identical to what Option B already produces once the collision is accounted for. The interesting divergence between C and C1 is specific to the default translation strategy; see the companion report.↩︎
